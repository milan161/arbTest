## 一、 基金配置文件 `lof_config.yaml` 的三大核心字段职能

`lof_config.yaml` 是整个套利系统的唯一核心配置源，控制着每只监控基金在系统中的运行方式。每只基金的配置围绕以下三大职能展开：

### 1.1 分流职能

- `category` (String): 主分类 TAB。决定基金显示在前端主看板的哪个 TAB（如：黄金原油、QDII欧美、QDII日本、QDII亚洲、国内LOF、现金管理、白银）。
- `sub_category` (String): 子分类。控制估值引擎对具体计算公式的选择（如：原油、黄金、纯ETF、指数、其他）。

### 1.2 估值职能

- `woody_supported` (Boolean): 是否支持 Woody API。
- `position` (Float) / `holdings.equity_ratio` (Float): 底仓仓位百分比（如 `88.45`），用于计算现金与持仓的配比。
- `valuation_portfolio` (List): 估值一篮子底层组件及理论权重分配。
- `related_index` (String): 关联指数代码，在 Woody 数据不支持时用作估值计算的参考基准。
- `rate_type` (String, 可选): 若为 `spot`，表示实时估值必须取新浪 USD/CNY 实时在岸汇率；若缺省，则取央行中间价（`usd_cny_mid`）。

### 1.3 对冲职能

- `trade_etf` (String): 套利交易对应的 ETF 现货代码（如 `USO`, `GLD`, `XOP`）。
- `trade_future` (String): 套利对冲对应的主力期货合约代号（如 `MCL`, `GC`, `CL`）。
- `future_hedging` (List): 期货对冲详情。包含期货标的、权重、到期月份等。*(注：目前对冲主要采用 ETF 现货，期货对冲尚未完全成熟，之前旧版设计的 Beta 系数调节逻辑已被废弃)*
  ```yaml
  future_hedging:
    - symbol: MCL            # 微原油期货
      delivery_month: '2604'   # 合约月份
      weight: 100.0          # 期货权重
      currency: USD
      exchange: SMART
  ```

## 二、 核心基金分类之“估值与对冲”算法详解

本套利系统最核心的价值在于“黄金原油”、“QDII欧美”、“QDII日本”三大类基金的估值和对冲实现。

### 2.1 黄金原油 (Woody API 支持，大宗商品跟踪)

#### 2.1.1 估值算法：矩阵公式 (Basket Valuation)

- **适用条件**：黄金原油基金（`fund_basket_weights` 有记录或 YAML 中配置有多只估值标的，如南方原油 501018）。
- **数学公式**：  
  $\text{实时估值} = \text{NAV}_{T-1} \times \left(1.0 + \text{position} \times \left( \left(\sum_{i} \text{price\_ratio}_i \times \text{weight}_i \right) \times \text{fx\_ratio} - 1.0\right)\right)$
  - $\text{price\_ratio}_i = \frac{\text{当前实时价}_i}{\text{基准日收盘价}_i}$
  - $\text{fx\_ratio} = \frac{\text{当前汇率}}{\text{基准日汇率}}$
- **锚点 (Anchor) 机制与时差处理**：  
  为了应对全球市场时差，估值篮子中包含带区域后缀的锚点（如 `^USO-EU`, `^USO-JP`, `^USO-HK`）。
  - **分母部分（基准日收盘价）**：使用带后缀符号（如 `^USO-EU`）查询数据库 `usa_etf_daily_prices` 对应的历史收盘价格。
  - **分子部分（当前实时价）**：去掉后缀和 `^` 前缀，直接获取美股 `USO` 的当前最新成交价进行实时计算。
  - **多空头寸保留**：支持负权重，限制过滤时必须使用 `weight != 0`，不得使用 `weight > 0` 过滤，以保留对冲和空头头寸。

#### 2.1.2 对冲算法

- **对冲工具选择**：交易 YAML 配置中的 `trade_etf` (如 USO, GLD) 现货，或根据 `future_hedging` 中的期货参数（如 MCL 微原油期货）对冲。
- **对冲数量换算**：目前主流采用等市值换算（即套利持仓市值除以期货合约乘数与价格）。*(纯期货校准及估值算法待进一步研发)*

---

### 2.2 QDII欧美 (Woody API 支持，欧美 ETF/指数跟踪)

#### 2.2.1 估值算法：魔法公式 (Magic Valuation)

- **适用条件**：单一 ETF 欧美基金，且 Woody 提供了对冲因子 `hedge`（如华宝油气 162411 对应 XOP）。
- **数学公式**：  
  $\text{实时估值} = \text{NAV}_{T-1} \times (1.0 - \text{position}) + \frac{\text{ETF当前实时价} \times \text{当前汇率}}{\text{hedge}}$
  - $\text{hedge}$ 反映基金净值与美股标的价格的换算关系（由 Woody API 每日更替，反映基金经理的对冲持仓占比）。
  - **在岸价汇率机制 (`spot`)**：对配置了 `rate_type: spot` 的在岸价基金（如 `513350` 富国标普石油、`159518` 嘉实标普石油、`159502` 嘉实标普生物），其“当前汇率”严格取盘中新浪 USD/CNY 实时在岸价。当在岸价接口超时失效时，跳过估值以防止算错。其他普通基金的当前汇率则取央行中间价。

#### 2.2.2 对冲算法

- **对冲工具选择**：通常直接交易美股对应 ETF（如 XOP, XBI, XLY）进行日内对冲，无期货合约对冲。

---

### 2.3 QDII日本 (有 Woody 数据，跟踪日经225 / 日经225期货)

#### 2.3.1 估值算法：静态用指数公式，实时用 NK 期货标准公式

- **静态估值（step4）**：使用日经225指数公式（N225），**不读 hedge**，与 Woody 网站及用户 Excel 做法一致。  
  $\text{静态估值} = \text{NAV}_{T-1} \times \left(1.0 + \text{position} \times \left( \text{idx\_ratio} \times \text{fx\_ratio} - 1.0\right)\right)$
  - $\text{idx\_ratio} = \frac{\text{日经225基准实时值}}{\text{基准日日经225收盘值}}$，$\text{fx\_ratio} = \frac{\text{日元当前汇率}}{\text{基准日日元汇率}}$，$\text{position}$ 默认 0.95。
- **实时估值（盘中推演）**：走专用 NK 期货标准公式（`fund_service.py` 路径A），**全程不读 `fund_daily_factors.hedge`**：  
  $\text{实时估值} = \text{NAV}_{base} \times \left((1-\text{position}) + \text{position} \times \frac{\text{NK当前实时价}}{\text{NK基准结算价}} \times \frac{\text{日元当前在岸价}}{\text{日元基准汇率}}\right)$
  - 依赖：新浪 `hf_NK` 实时价 + `futures_daily` 的 NK 结算价 + 日元在岸价 + N225 基准(Yahoo/新浪) + 东财基金净值。
  - `dynamic_valuation.calculate()` 对 QDII日本 失效（NKY 在 `usa_etf_daily_prices` 无数据）→ 实际由路径A 完成。
- **Woody 角色**：QDII日本 在 Woody 中**确有 hedge 记录**，且 `hedge = NKY_close × JPYCNY_close / (NAV_close × pos)` 与数据库存储值完全吻合（1.0000）；但实时估值采用 NK 期货路径，并不消费该 hedge 字段。

#### 2.3.2 对冲算法

- **对冲工具选择**：属于指数型 QDII，通常不进行日内对冲，主要进行场内折溢价申赎套利。

### 2.4 估值引擎分层：静态估值 vs 实时估值（2026-07-27 增补）

系统存在**两套相互独立**的估值引擎，过去多次因混淆二者导致显示与运行时不一致，必须区分清楚：

| 维度        | 静态估值（盘后 step4）                              | 实时估值（盘中看板推演）                                                                |
| --------- | ------------------------------------------- | --------------------------------------------------------------------------- |
| 触发入口      | `daily_updater` → `static_valuation.py`     | 看板推演：`dynamic_valuation.calculate()`（单一ETF类）+ `fund_service.py` 路径A（QDII日本） |
| 结果落库      | 写入 `unified_fund_history.static_val`（盘后一次性） | 不落库，盘中高频刷新展示                                                                |
| 是否读 hedge | 仅 `etf`/`''` 类先试 magic(hedge)，缺失降级矩阵        | 单一ETF类 Tier1 magic(hedge)/Tier2 矩阵；QDII日本 不读 hedge                          |

**静态估值分发逻辑**（`static_valuation._deduce_valuation`）：

1. `valuation_method='index'/'equity_asia'/'lof_domestic'` → **指数公式，无 hedge，直接 return**（161125/161130 用 .INX/.NDX；QDII日本用 N225）。
2. `valuation_method=''` 或 `'etf'` → 先试**魔法公式（消费 Woody hedge）**，hedge 缺失/算不出则降级**矩阵公式**（162411 如此）。
3. `valuation_method='basket'` → **矩阵公式**（黄金原油）。

**实时估值分发逻辑**：

- 162411 / 161125 / 161130（单一ETF + hedge）：`dynamic_valuation.calculate()` → **Tier1 魔法(Woody hedge) / Tier2 矩阵(无 hedge 兜底)**。hedge 本质解决 ETF 净值获取（实时只有价、净值需 Yahoo 翻墙），兜底用从 Yahoo 采集的 ETF 净值。
- QDII日本：`fund_service.py` 路径A → **NK 期货标准公式**，不读 hedge，直接用新浪 `hf_NK` + `futures_daily` 结算价（期货新浪有历史结算价，天然可兜底）。

**估值-对冲参数一致性原则**：

- **静态估值不适用**此原则：161125/161130/QDII日本 静态直接用指数，不消费 hedge 字段。
- **实时估值适用**：对冲用 ETF/期货 → 估值也必须用 ETF/期货（非指数）。故实时走 magic/矩阵（ETF 价）或 NK 期货，不混用指数。

**hedge 三类（不可刻舟求剑，2026-07-27 明确；同日用 Woody API 真实 JSON 数值核对精确语义）**：

> **hedge 精确语义（数值核对结论）**：Woody API 每只基金均返回独立的 `position` 字段（如 513000=0.93、513880=0.91、162411=0.95）。恒等式 **`hedge = calibration / position`**（含仓位）精确成立（相对误差 1e-12 量级）；`calibration = 基准价 × 基准汇率 / 净值`（**不含仓位**）。  
> **hedge 的计价标的因基金而异，严禁混用**：
>
> - 162411：calibration 与 hedge 均以 **XOP** 计价（`1286.68/0.95=1354.40` ✓）；
> - 161125/161130：calibration 以 **SPX/NDX 指数**计价，hedge 以 **SPY/QQQ ETF** 计价，`calib/pos ÷ hedge` = SPY/QQQ 的换算系数（10.0332 / 41.1100，即 API 中 SPY/QQQ 自身的 calibration）；
> - 513000/513880：calibration 与 hedge 均以 **znb_NKY 日经期货**计价（与 N225 现货指数存在期现基差）。  
>   因此 hedge 能否使用取决于「当前估值路径取的价格标的」是否与 hedge 计价标的一致——静态取指数价（.INX/.NDX/N225）时 161125/161130/513000 禁用 hedge；实时取 SPY/QQQ 价时 161125/161130 可用。

> **★ 核心原则（永久，2026-07-27 深夜东哥确认）：hedge 计价标的一致性原则**  
> hedge 能不能用，只取决于一件事——**「估值时实际取价的标的」与「hedge 计价标的」是否一致**：
>
> - 一致（162411 取 XOP 价、161125/161130 实时取 SPY/QQQ 价）→ 可用魔法公式；
> - 不一致（161125/161130 静态取 .INX/.NDX 指数价、513000 静态取 N225 现货价）→ 禁用 hedge，改走指数公式或矩阵公式，否则数量级 / 期现基差错位。  
>   此原则与「估值-对冲参数一致性原则」（对冲用 ETF/期货 → 估值也用 ETF/期货）互补但不同层：本原则管 **hedge 因子可用性**，后者管 **对冲-估值标的一致**。代码落点：`valuation_data_engine.py` 的 `hedge_allowed(method, category, mode)`，由 yaml `valuation_routing` 配置驱动；黄金测试 `test_unified_valuation.py` #7/#8 守卫。

- **A 类 单ETF/单指数**（162411/161125/161130/QDII日本）：`fund_daily_factors` 有 hedge 记录，数学上 `hedge = 单标的基准价×对应币种汇率/(基金净值×仓位)`（以其计价标的表述），可由公开数据复算；**程序实时估值仍使用 Woody 提供的 hedge 值**。
- **B 类 多篮子**（黄金原油等约13只）：`fund_daily_factors` **无 hedge 记录**（woody 多篮子 hedge 含 -EU/-JP 等程序无数据标的、且缺 EUR 中间价，无法完整自算）；程序实时走**无 hedge 矩阵公式**，但篮子**权重/仓位来自 Woody API（yaml 配置）**，并非完全独立。
- **C 类 个别残留**（如 164824 印度）：hedge 极旧（2026-05）且基于程序无数据标的，属死字段。

### 2.5 统一估值核心模块（估值引擎 + 数据引擎分离，2026-07-27 落地）

所有估值算法在数学上等价于同一个**篮子矩阵公式**，魔法公式只是"单组件 + hedge 常量折叠"。据此将代码拆分为两层（与 woody `EstNetValue` 的 `arSrc` 注入模式一致）：

- **估值引擎（公式层，不碰数据源）**：`arbcore/calculators/unified_valuation.py` 的 `basket_valuation(nav, pos, components, fx_base, fx_now, hedge=None)`。
  - 单组件且 `hedge>0` → 魔法公式（O(1)）；否则走矩阵公式。
  - 历史别名 `valuation_math.py` 的 `magic/basket/index/asia/lof_premium` 五个函数现已**全部委托**到该核心，消除重复实现。
- **数据引擎（装配层，只整形不 IO）**：`arbcore/calculators/valuation_data_engine.py` 的 `assemble_static_components` / `assemble_dynamic_components`。
  - 调用方（数据库 / IB / 富途 / 新浪 / TDX）取好价格后，以 `{symbol: 现价}` 注入；本层只把 ETF/指数/期货价整形为 `components`，**不读库、不爬网**。
  - **hedge 路由（yaml 配置驱动，2026-07-27 起）**：由 `lof_config.yaml` 顶层 `valuation_routing` 节统一决策，含 `methods`（每种 `valuation_method` 的 `static_hedge` / `dynamic_hedge` 开关）与 `category_fallback`（基金未配置 `valuation_method` 时按类别兜底，如 513000 的 `valuation_method=''` → QDII日本 → index）。规则依据 hedge 计价标的：静态路径取指数价（.INX/.NDX/N225），与 161125/161130（SPY/QQQ 计价）、513000（NKY 期货计价）的 hedge 标的不一致 → `static_hedge=false`；实时路径取交易标的价（SPY/QQQ/XOP），与 hedge 计价一致 → index/etf 类 `dynamic_hedge=true`。误用后果：161125/161130 差 10 倍/41 倍，513000 引入期现基差。
- **调用点**：
  - 静态估值 `static_valuation.py._deduce_valuation` → 数据引擎装配 → 统一核心。
  - 实时估值 `dynamic_valuation.py.calculate` **直调**数据引擎装配 + 统一核心（2026-07-27 起不再经 `valuation_math` 间接）；QDII日本实时（`fund_service.py` 两段 NK 期货逻辑）已改为注入 NK 期货价走统一核心，消除原先的独立内联重复实现。
- **安全约束**：hedge 数学恒等式不可改写（魔法公式 = `nav*(1-pos) + (price*fx)/hedge`）；任何改动须经 `arbcore/scripts/test_unified_valuation.py` 黄金测试（已知基金反算误差须 0.000%）方可上线。

### 2.6 通俗版：basket_valuation 到底怎么被调用（面向非技术）

这一段专为非编程背景的读者写，回答三个最常问的问题：**① 程序里还有 static/dynamic 吗？② basket_valuation 的参数是什么？③ 它怎么"知道"该用哪个公式？**

#### Q1：程序里只有 basket_valuation 一个函数，static_valuation / dynamic_valuation 都没了吗？

**都还在，没有被删。** 只是它们从"自己写公式"变成了"调用统一核心"。整个系统分三层（见下图）：

![估值系统三层分工](local-file:///D:/Study/arbTest/docs/assets/valuation_three_layer.svg)

- **底层 · 计算核心**：`unified_valuation.py` 的 `basket_valuation()` —— 唯一的公式实现。
- **中层 · 数据引擎**：`valuation_data_engine.py` —— 读配置、把价格整形为输入。
- **上层 · 两个入口**：`static_valuation.py`（静态估值）、`dynamic_valuation.py`（实时估值）—— 都委托给下面两层。

> 数据采集层（woody API / IB / 新浪 / TDX）**只负责取数**，把 `{标的代码: 现价}` 交给数据引擎，完全不碰计算公式。所以"估值引擎优化"和"数据采集"是解耦的——昨天我们动的只是估值引擎，取数那一层原封没动。

#### Q2：basket_valuation 的参数到底是什么？是基金代码、日期、静态/实时标志吗？

**不是。** 它只收 6 个数字（或数字列表），**不认识任何基金的名字、不知道日期、不区分静态还是实时**：

```python
basket_valuation(base_nav, position, components, fx_base, fx_now, hedge=None)
```

| 参数           | 含义                               | 例子                                              |
| ------------ | -------------------------------- | ----------------------------------------------- |
| `base_nav`   | 基金 T-1 净值                        | 162411 的 7.20                                   |
| `position`   | 仓位比例                             | 0.95                                            |
| \`components | 组件列表，每项 = `{标的代码, 当前价, 基准价, 权重}` | 黄金 = `[{GLD, 372.5, 371.5, 0.53}, {GLD-EU, …}]` |
| `fx_base`    | 基准日汇率                            | 7.20                                            |
| `fx_now`     | 当前汇率                             | 7.18                                            |
| `hedge`      | 可选，hedge 常数（单组件+hedge 时走魔法）      | 1354.40（162411）                                 |

> 关键点：函数本身**是"哑"的**——你喂什么数字它算什么，它既不查数据库、也不读配置、也不知道"我是谁"。这正是它能同时服务静态估值和实时估值的原因：区别只在"谁给它喂数字"（数据引擎），而不在函数内部。

#### Q3：它怎么"知道"哪只基金该用哪个公式？——  "映射表格"

在代码里就是 **`lof_config.yaml` 的配置映射表**（每只基金的 `category` / `valuation_method` / `valuation_portfolio` + 顶层 `valuation_routing` 节）。但**这张表函数自己不读**，分流分两步、都在函数**外面**完成：

![basket\_valuation 路由分流](local-file:///D:/Study/arbTest/docs/assets/valuation_routing.svg)

- **第①步（函数内·数学自动）**：核心只看 `hedge` 是不是有效值 + 组件是不是只有 1 个。`hedge>0 且只有 1 个组件` → 魔法公式；否则 → 矩阵公式。这是纯数学判断，**不存在"认错基金"的可能**。
- **第②步（函数外·数据引擎读 yaml）**：数据引擎按映射表替它把"该喂的数字"准备好——决定 `components` 里放哪些标的、`hedge` 带不带值。

几个例子你就明白怎么分流：

| 基金                     | yaml 映射（类别/方法）                 | 数据引擎喂给核心的             | 核心走        |
| ---------------------- | ------------------------------ | --------------------- | ---------- |
| 162411（单 ETF XOP）      | `category: QDII欧美`             | 单组件 + `hedge=1354.40` | 魔法         |
| 161125（静态取 .INX）       | `category: QDII欧美` + 静态禁 hedge | 单组件 + `hedge=None`    | 矩阵（指数）     |
| 161125（实时取 SPY）        | 同上 + 实时允许 hedge                | 单组件 + `hedge>0`       | 魔法         |
| 513000（QDII日本静态取 N225） | `category: QDII日本` + 静态禁 hedge | 单组件 + `hedge=None`    | 矩阵（NK 期货价） |
| 黄金原油（多篮子）              | `category: 黄金原油`               | 多组件 + `hedge=None`    | 矩阵         |

> 为什么 513000 静态必须 `hedge=None`？因为它的 hedge 计价标的是 NK**期货**价，而静态取的是 N225 **现货**价（含期现基差），两者不一致 → 按 §2.4「hedge 计价标的一致性原则」禁用 hedge，改走矩阵。这条路由由 `valuation_routing` 的 `category_fallback`（QDII日本 → 静态禁 hedge）卡住，并有黄金测试守卫。

**一句话总结**：`basket_valuation` 是唯一公式、是"哑计算器"；"银色表格"（yaml 映射）由数据引擎读取，替它把输入准备好，从而间接决定走魔法还是矩阵。想调整路由只看 yaml，不用改核心代码。

> 映射表里每个字段（`category` / `valuation_method` / `valuation_portfolio` / `valuation_routing`）的逐字段说明，见 `docs/004_基金配置文件lof_config.yaml说明.md`。

为了防止净值更新时引入时效重影，静态/实时溢价率计算**必须且只能使用前一日（T-1）净值**：

## 1. 估值核心因子的数学本质

系统中进行盘中动态估值和盘后静态计算主要依赖两个关键因子：**校准因子 (Calibration)** 和 **对冲因子 (Hedge)**。这两个因子均来自每日 Woody API 数据同步。

### 1.1 校准因子 (Calibration)

- **数学定义**：  
  $\text{Calibration} = \frac{\text{基准ETF价格}_{T-1} \times \text{汇率}_{T-1}}{\text{净值}_{T-1}}$
- **物理意义**：代表在 $T-1$ 日（基准日），每 $1$ 份 LOF 基金净值在理论上等价于多少人民币价值的底层 ETF 组件。

### 1.2 对冲因子 (Hedge)

- **数学定义**：  
  $\text{Hedge} = \frac{\text{Calibration}}{\text{position}} = \frac{\text{基准ETF价格}_{T-1} \times \text{汇率}_{T-1}}{\text{净值}_{T-1} \times \text{position}}$
- **物理意义**：代表大约需要多少份底层标的 ETF，才能完美对冲 $1$ 份基金净值（结合了仓位因素）。
- **常量折叠**：Woody API 会根据基金经理每日的真实仓位，在后台计算出这一比率并直接传递。通过引入 $\text{Hedge}$，系统能够将原本复杂的篮子权重计算折叠为 $O(1)$ 的简单算术，极大地提高了高频实时估值的计算效率。

---

## 2. 核心估值公式的实现与数学证明

根据基金的不同种类与因子的缺失状态，系统分别调用以下核心估值公式：

### 2.1 魔法公式 (Magic Valuation)

- **适用条件**：单一 ETF 欧美基金且 Woody 提供了对冲因子 `hedge`（如华宝油气 162411 对应 XOP）。
- **公式实现**：  
  $\text{估值} = \text{NAV}_{T-1} \times (1.0 - \text{position}) + \frac{\text{ETF实时价}_T \times \text{汇率}_T}{\text{Hedge}}$
- **物理等价性证明**：  
  魔法公式将基金净值拆分为**非持仓现金部分**（用上一交易日真实净值计价，即 $\text{NAV}_{T-1} \times (1 - \text{pos})$）与**持仓部分**（按标的实时价格和实时汇率换算）。  
  将 $\text{Hedge}$ 的定义带入上式：  
  $\text{估值} = \text{NAV}_{T-1} \times (1.0 - \text{position}) + \frac{\text{ETF实时价}_T \times \text{汇率}_T}{\frac{\text{ETF价格}_{T-1} \times \text{汇率}_{T-1}}{\text{NAV}_{T-1} \times \text{position}}}$  
  进一步化简：  
  $\text{估值} = \text{NAV}_{T-1} \times (1.0 - \text{position}) + \text{NAV}_{T-1} \times \text{position} \times \left( \frac{\text{ETF实时价}_T}{\text{ETF价格}_{T-1}} \times \frac{\text{汇率}_T}{\text{汇率}_{T-1}} \right)$  
  提取公因式 $\text{NAV}_{T-1}$：  
  $\text{估值} = \text{NAV}_{T-1} \times \left( 1.0 + \text{position} \times \left( \frac{\text{ETF实时价}_T}{\text{ETF价格}_{T-1}} \times \frac{\text{汇率}_T}{\text{汇率}_{T-1}} - 1.0 \right) \right)$  
  证明完毕。该式在数学上完全等价于**以基准日净值为锚点，乘以持仓资产在日内的价格和汇率变动幅度**。

### 2.2 矩阵公式 (Basket Valuation)

- **适用条件**：黄金原油等拥有多资产持仓篮子的基金（`fund_basket_weights` 有多条权重记录，或魔法公式因缺少 hedge 因子降级时）。
- **公式实现**：  
  $\text{估值} = \text{NAV}_{T-1} \times \left( 1.0 + \text{position} \times \left( \left(\sum_{i} \frac{\text{ETF实时价}_{T, i}}{\text{ETF价格}_{T-1, i}} \times \text{weight}_i\right) \times \frac{\text{汇率}_T}{\text{汇率}_{T-1}} - 1.0 \right) \right)$
- **多空头寸与负权重支持**：当篮子持仓中包含负权重（空头头寸）时，传统的 `weight > 0` 过滤规则会将负权重的对冲成份误杀剔除。因此，系统算法严格使用 `weight != 0` 过滤，以保留对冲和反向头寸，确保矩阵计算在多空市场下的准确性。

### 2.3 指数公式 (Index Valuation)

- **适用条件**：`valuation_method='index'/'equity_asia'/'lof_domestic'` 的基金静态估值（含 161125/.INX、161130/.NDX、QDII日本/N225）。QDII日本 实时另有 NK 期货专用路径（见 2.3 正文）。
- **公式实现**：  
  $\text{估值} = \text{NAV}_{T-1} \times \left( 1.0 + \text{position} \times \left( \frac{\text{实时指数}_T}{\text{基准指数}_{T-1}} \times \frac{\text{日元汇率}_T}{\text{日元汇率}_{T-1}} - 1.0 \right) \right)$
  - $\text{position}$ 默认取 `pos_ratio`（默认为 95%）。

## 3. 实时估值中的汇率控制机制

系统支持根据基金的不同特性，采用不同的实时汇率数据源以最大化拟合基金净值的真实涨跌。

### 3.1 央行中间价与实时在岸价 (Spot FX) 的区分控制

在 `lof_config.yaml` 配置文件中通过 `rate_type` 字段进行控制：

1. **在岸价基金 (Spot Rate 基金)**：  
   对于配置了 `rate_type: spot` 的基金（如富国标普石油 513350、嘉实标普生物 159502），这些基金使用在岸人民币汇率对净值进行计价。
   - 实时计算时，系统直接从新浪获取实时 USD/CNY 在岸价作为“当前汇率”。
   - 为保障盘中高频刷新的可靠性，在岸价缓存 TTL 设定为 15 秒。
   - **安全防降级机制**：若新浪在岸价接口超时或返回无效数据，系统将**放弃并跳过该基金的估值**，绝对禁止使用央行中间价进行降级兜底，以防发生错误的折溢价计算造成实盘亏损。
2. **普通基金**：  
   对于未配置 `rate_type: spot` 的基金，其“当前汇率”和“基准汇率”统一使用央行每日公布的人民币汇率中间价 `usd_cny_mid`。由于中间价在交易日内是不变的，系统在盘中直接读取内存快照以降低数据库 IO 开销。

## 4. 美国假期回溯与时差处理机制

QDII 欧美基金在盘中估值时面临严重的交易时差和节假日不对称问题：

- **交易时差**：A 股交易时间（9:30-15:00）美股已收盘，因此 $T$ 日 A 股盘中所使用的“ETF 实时价”实际上是美国前一天（即 $T-1$ 日）的收盘价。
- **假期不对称**：若 $T-1$ 日是美国假期（美股休市），而 $T$ 日 A 股正常交易。此时虽然系统获取了最新的基金净值 $\text{NAV}_{T-1}$（由于基金公司估值日为 $T-1$ 日），但由于美股休市，数据库中没有这一天任何美股 ETF 的价格数据。

### 4.1 假期回溯算法

在 `dynamic_valuation.py` 中，针对包含美股的分类（黄金原油、QDII欧美等），系统在加载 $T-1$ 日基准数据时，会通过 SQL 校验 `usa_etf_daily_prices` 在此基准日是否包含有效的 ETF 价格。

- 如果 `etf_count == 0`，代表最新净值日 $T-1$ 美国处于休市状态。
- 系统会**向前自动回溯**，定位到最近一个既有基金净值、又有美股 ETF 历史收盘价的有效交易日作为实际的基准日，获取对应的基准价格与基准汇率。
- 该机制完美避免了因基准日底层数据缺失而导致盘中动态估值失效、出现归零脏数据或误报警的情况。

## 5. hedge 缺失时的降级路径与净值映射

当 Woody API 提供的 `hedge` 因子暂不可用时，估值计算器会自动降级到数学等价的矩阵公式兜底，保证估值连续性（详见 2.4 分发逻辑）。

### 5.1 兜底原理：COALESCE 与矩阵公式降级

当魔法公式由于缺少 `hedge` 无法执行时，代码会自动降级执行 **矩阵公式 (Basket Valuation)**。矩阵公式需要获取底层 ETF 的 $T-1$ 日基准分母。

在 `static_valuation.py` 和 `dynamic_valuation.py` 中，查询基准数据的核心 SQL 语句均为：

```sql
SELECT symbol, COALESCE(NULLIF(netvalue, 0), price) as price FROM usa_etf_daily_prices
```

这句 SQL 是兜底逻辑的核心：

1. 它优先提取由 `US_etf_nav.py` 采集落库的 **`netvalue`**（ETF 官方日终净值）。
2. 只有当 `netvalue` 缺失时，才会退化使用 `price`（收盘价）。

### 5.2 降级公式的数学等价性

Woody 的 `hedge` 本质上是由公式推导出的乘数比例：  
$\text{Hedge} \approx \frac{\text{美股ETF净值} \times \text{汇率}}{\text{基金净值} \times \text{仓位}}$

而当系统降级使用矩阵公式，并将分母精准地替换为采集落库的 `netvalue` 时，我们计算所使用的波动率基准与 Woody 计算 `hedge` 所用的基准在数学上是 **100% 等价的**。

### 5.3 适用范围

- **已覆盖兜底的标的**：`XOP` (华宝油气等)、`SPY` (标普500 LOF)、`QQQ` (纳指 LOF) 等。这些代码已被纳入每日定时的 `US_etf_nav.py` 采集列表，确保每日 `netvalue` 入库，可走矩阵公式降级兜底。
- **QDII日本的特殊路径**：QDII日本 实时估值走 NK 期货标准公式（`fund_service.py` 路径A），**不读 `hedge`**，因此不存在“hedge 缺失降级”的问题；其基准来自新浪 `hf_NK` 实时价 + `futures_daily` NK 结算价，期货本身有历史结算价，天然可兜底，无需依赖 ETF 净值反推。

| 数据采集 | woody / IB / 新浪 / 腾讯K线 | **原样搬**，改为服务端定时拉取 | 100% |
| 数据库 | 本地 SQLite | 迁云数据库(MySQL/PostgreSQL)，表结构直接迁移 | 高 |
| 展示层 | Vue 浏览器端 | **重写**为微信小程序(WXML/WXSS/JS) | 需重写 |
| 调度 | 本地 `daily_updater` | 云服务器 cron / 定时任务 | 中 |

**三阶段路线**：

1. **阶段一 · 稳定版（当前进行中）**：完成估值引擎重构、Bug 修复（收盘价快照锁死已修）、逐个基金静态估值验算、文档固化。这是小程序化的地基——算法必须先稳。
2. **阶段二 · 后端上云**：买云服务器(腾讯云) + 域名(ICP 备案) + HTTPS；把 Flask 估值 API 与采集定时任务部署上去，用小程序可访问的 HTTPS 域名暴露接口。此阶段后端代码基本不动。
3. **阶段三 · 小程序前端**：注册微信小程序账号（企业号，300 元/年认证；个人号金融内容受限），用 WXML/WXSS/JS 重写展示层（基金列表 / 详情 / 历史 / 溢价趋势 / 自选预警），调用阶段二的 API。

**微信平台硬约束（必须前置）**：

- 小程序后端**必须 HTTPS + 已备案域名**（国内），不能直连本地 SQLite / 局域网。
- 交易仍走**本地 QMT**，小程序**只做展示与溢价预警**，不触碰下单（合规 + 安全）。
- 基金/套利属金融内容，个人主体小程序可能受限，建议用**企业主体**注册。

**投入估算**：阶段二（云 + 备案）约 1–2 周；阶段三（前端重写）约 2–3 周；阶段一（稳定版）是前置必要条件，当前优先。架构图见 `docs/assets/wechat_miniprogram_arch.svg`（与本文 §七 同步）。

> 备注：本路线图是东哥的"产品化梦想"，非当前必须项；当前主线仍是阶段一的稳定版与文档。时机成熟时再启动阶段二/三。
