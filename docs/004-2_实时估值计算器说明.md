# 实时估值计算器（Real-time Valuation Calculator）技术说明

> 最后更新：2026-07-30
> 目的：让后续 AI 明确——**本程序内存在一套"实时估值计算器"**，它既能算实时估值（rt_val），也能算对冲数量（hedge quantity）。
> 本文聚焦**沙盘页前端计算器**（`useValuationCalculator.ts`）与**后端实时估值引擎**（`DynamicValuationCalculator` / `calc_quantity.py`）两条代码路径；
> 覆盖 **①单 ETF 魔法公式（T1）** 与 **②期货校准 ETF（T2）** 两类基金的「实时估值 + 对冲数量」；
> **③纯期货** 留空待补（见第十节）。

---

## 一、这份文档解决什么问题

2026-07-30 东哥用一整批 woody 微信套利信号逐条考试，确认了程序实时估值/对冲数量与 woody 完全对齐。后续 AI 在改实时估值或对冲面板时，必须先读本文，避免：

1. **误以为程序只有"历史静态估值"**——其实还有盘中实时估值计算器（沙盘页 / 主面板 rt_val 后端现算）。
2. **混淆"魔法公式"与"矩阵公式"的适用边界**——单 ETF 走恒定 hedge 魔法；多篮子走矩阵；别刻舟求剑。
3. **用 LOF 市价代替净值 NAV 算对冲敞口**——这是已定位但尚未修复的 bug（见第九节）。
4. **分不清 hedge / calibration 的语义**——hedge 是 LOF↔ETF 兑换比；calibration 是 期货↔ETF 兑换比。两者量级、单位都不同，别混。

> 关联文档：`004-1_历史记录静态估值说明.md`（static_val）、`004_0_主面板布局与数据来源说明.md`（主面板 rt_val 后端分支、2026-07-30 休市返回 None 的 bug 修复）。

## 三、两类基金与算法路由（本文覆盖范围）

| 类型 | 典型基金 | 实时估值算法 | 对冲数量算法 |
|------|---------|------------|------------|
| **A. 单 ETF 魔法公式（T1）** | 162411(XOP)、161125(SPY)、161130(QQQ)、QDII日本(NK) | 魔法公式（恒定 hedge） | `etf_qty = round(lof_qty / hedge)` |
| **B. 期货校准 ETF（T2）** | 160719(GLD+MGC)、163208(USO+原油)、501018(USO变体+MCL) | etfVal 篮子 **或** futCalibVal 期货校准 | `lofQtyFuture`（按期货手数反推 LOF） |
| C. 纯期货 | （如 NK 直接估值） | — | — | **本文留空，见第十节** |

**路由判定逻辑（前端 `useValuationCalculator.ts`）**：
- `portfolio.length === 1 && hedge > 0` → 魔法公式（T1）

- `category === 'QDII日本'` → 走纯期货（`pureFutVal`/`lofQtyPureFuture`，即类型 C，留白）

## 四、类型 A：单 ETF 魔法公式（T1）

### 4.1 实时估值

```
rt_val = base_nav × (1 − position) + (current_etf_price × current_fx) / hedge
```

- `base_nav`：基准日（T-1 或 T-2，依 Tab）净值，来自 `unified_fund_history.nav`
- `position`：仓位比例（小数，如 0.96），来自 `fund_daily_factors.position`（缺失时 fallback yaml `position/100`）
- `current_etf_price`：标的 ETF 实时价（如 XOP），来自实时行情优先级链
- `current_fx`：当前 USD/CNY 中间价
- `hedge`：**恒定对冲比 H**，见 4.2

代码位置：
- 前端：`useValuationCalculator.ts :: etfVal`（line 241-258，单标的 / trade_etf 兜底两条）
- 后端：`unified_valuation.basket_valuation` 的 `hedge>0 && len(components)==1` 分支（line 51-55）
- 后端 H 合成：`fund_service.py :: get_base_data` 周边（line 2372-2386）：DB hedge 空时
  `calc_hedge = (base_etf_price × base_fx) / (base_nav × base_pos)`

### 4.2 恒定对冲比 H 魔法（核心概念）

`hedge`（即 H）是 woody 每日算好的**常数**，语义 = **「每份 LOF 对应多少份标的 ETF 敞口」（以 RMB 计）**。

```
H = (基准日 ETF 价 × 基准日 fx) / (基准日 LOF 净值 × 仓位)
```

**为什么叫"魔法"**：分子分母里的基准日价格、汇率全部是"基准日那一刻的快照"，因此 H 是个**固定常数**，实时估值时直接拿 H 当转换器，无需再算一次篮子。这也是 woody 把 H 预先算好存进 `fund_daily_factors.hedge` 的原因——高频实时算得快。

实例（162411 华宝油气，单一 XOP）：
- `fund_daily_factors.hedge = 1350.896286`（恒定，程序已落库）
- 实时：`rt_val = 0.91×(1−pos) + (XOP价×fx)/1350.896286`
- 东哥考试验证：给定 LOF 810500 股 → 程序自判单 ETF → `etf_qty = round(810500/1350.896286) = 600` 股 XOP ✅

### 4.3 对冲数量

```
etf_qty = max(1, round(lof_qty / hedge))
```

- 前端：`useValuationCalculator.ts :: lofQtyEtf`（line 463-467）
- 后端：`calc_quantity.CalcQuantity.etf_hedge`（line 77）

对称于 4.2：`LOF数量 = round(etf_qty × hedge)`，两条路径互逆，构成"物理兑换比"闭环（详见东哥公众号《08_实战篇_精准计算对冲数量的数学魔法》）。

## 五、类型 B：期货校准 ETF（T2）

T2 基金同时持有"ETF 篮子"和"对应期货"，提供**两种实时估值视角**与**一种对冲数量算法**。

### 5.1 实时估值视角一：ETF 篮子估值（etfVal 多标的分支）

与矩阵公式一致（同 `basket_valuation` 多组件路径）：

```
fx_change   = current_fx / base_fx
w_change    = Σ (current_price_i / base_price_i) × weight_i
net_ratio   = position × (w_change × fx_change − 1)
rt_val      = base_nav × (1 + net_ratio)
```

代码：`useValuationCalculator.ts :: etfVal`（line 260-289，多标的加权变化率）。

### 5.2 实时估值视角二：期货校准估值（futCalibVal）

把期货价换算成"等价现货 ETF 价"再套篮子：

```
equiv_spot   = fut_price / calibration          # 期货 → 等价 ETF 现货价
etf_change   = equiv_spot / base_etf_price       # 等价现货的涨跌幅
w_change     = Σ etf_change_i × normalized_weight_i
rt_val       = base_nav × (1 + position × (w_change × fx_change − 1))
```

代码：`useValuationCalculator.ts :: futCalibVal`（line 296-386，非指数分支 line 349-383）。

**⚠️ calibration 语义铁律**（最易错）：
- `calibration` = **期货 ↔ ETF** 的兑换比（如 `GC价/GLD价 ≈ 10.89`、`CL价/USO价 ≈ 0.657`），**不是** ETF↔LOF 的校准。
- 单 ETF 基金的 `hedge` 才是 ETF↔LOF 兑换比（见 4.2）。两者**不要混淆**。
- 程序取 calibration 来源：`fund_daily_factors.calibration` 缺失时，从 `futures_daily` 按 `GC/CL/NQ/ES` 等大品种兜底（`fund_service.py` line 2492-2512）。

### 5.3 对冲数量（按期货手数反推 LOF）

```
gldSharesPerContract = round(calibration × multiplier)   # 1 手期货 ≈ 多少份 ETF
displayHedgeValue    = hedge × gldSharesPerContract       # 1 手期货 ≈ 多少份 LOF
lof_qty              = targetLotsFuture × displayHedgeValue（取整百）
```

- 前端：`useValuationCalculator.ts :: lofQtyFuture`（line 505-535）
- 合约乘数 `multiplier`：MGC=10、GC=100、MCL=100、CL=1000、MNQ=2、NQ=20、MES=5、ES=50、AG=15（line 514-522）

**⚠️ 期货腿一律是微型合约（M 前缀）**：
- `hf_GC`/`hf_MGC` → 实际是 **MGC（微型黄金，10 oz/手）**，不是 GC（100 oz）。
- `hf_CL`/`hf_MCL` → 实际是 **MCL（微型原油，100 桶/手）**，不是 CL（1000 桶）。
- 东哥考试 501018：`hf_CL 1` = 1 手 MCL，1 手 MCL @85.32 ≈ $8,532 ≈ 65.6 个 USO 等价股，与 ETF 篮子 65 股**等值**（双表达，非叠加/替代）。

实例（160719 嘉实黄金，GLD+^GLD-EU，MGC 对冲）：
- 程序勾选"实时校准估值"时，期货对冲数量面板**能算**（DB hedge 空也由 `fund_service.py` 后端合成 `calc_hedge`）。
- 东哥考试：160900 股 LOF → `hf_GC 1`；107300 股 → `hf_GC 0`（期货腿不随 LOF 线性缩放，是固定参考锚，类比 1 手 MGC ≈ 整篮 ETF 名义）。

## 六、多区域变体篮子（501018 案例：减法规则 + NAV 基准）

501018（原油 QDII）持有 `USO` + `^USO-EU` + `^USO-JP` 三个区域变体。

### 6.1 减法规则（通用，N 区域）

woody 信号里 `USO 699` 是**整篮总数**（base 符号 = 含区域变体总数）。无期货腿时：
```
USO(纯美) = USO总数 − ^USO-EU − ^USO-JP = 699 − 393 − 196 = 110
```
有期货腿（GLD 类）时 `GLD X` = 美股纯量，与 `^GLD-EU` 相加构成整篮。规则对 2 区域 → N 区域通用，**不要当符号错位处理**。

### 6.2 NAV 基准铁律（关键 bug 来源）

篮子拆解的**敞口基准必须用 LOF 净值 NAV，不能用 LOF 市价**。

- 正确（NAV 基准）：`exposure = lof_qty × base_nav × position` → 501018 解出总和 **699**，与 woody 逐位吻合。
- 错误（市价基准）：`exposure = lof_qty × lof_price × position`（lof_price=2.041，NAV=1.6554，差 ×1.2329）→ 解出 ~809~862，即旧程序偏差来源。

东哥考试：
- 408600 股 → NAV 法：USO 109 / ^EU 390 / ^JP 200 = **699**（与 woody 699 精确吻合；个股 ±3~4 股来自权重快照错位，非方法错）
- 38000 股（×0.093 比例）→ USO 10 / ^EU 36 / ^JP 19 = 65（与 woody 37/18/10=65 总数一致，个股 ±1 取整差）

## 七、三套概念的统一关系（务必理解）

| 概念 | 来源 | 一句话 |
|------|------|--------|
| **恒定 H 魔法** | 程序单 ETF 路径（`etf_qty=round(lof_qty/hedge)`） | hedge 是基准日算好的常数，实时直接当转换器 |
| **NAV 基准铁律** | 篮子敞口必须用净值 | 敞口 = 数量×净值×仓位，不是数量×市价×仓位 |
| **Excel 四步法**（东哥） | 公众号方法论 | 把 H 魔法推广到篮子：①算基准日校准值 C ②H=C/仓位 ③LOF数量=本金/仓位/市价取整百 ④各ETF数量=LOF数量×权重/H |

**三者殊途同归**：最终每个 ETF 数量公式都不含实时 ETF 价、不含实时汇率——因为所有"动态变量"在 H 常数里被约掉了。这就是"恒定对冲比 H 魔法"的本质。

## 八、已知待修复 Bug（用户 2026-07-30 指令：先别急改）

**篮子对冲数量用了 LOF 市价而非净值**：

| 位置 | 当前代码 | 应为 |
|------|---------|------|
| 前端 `useValuationCalculator.ts:475` | `targetExposureRMB = finalLofQty * simLofPrice.value * pos` | `finalLofQty * base_nav * pos` |
| 前端 `:485` 拆解分母 | `(targetExposureUSD * weight) / cPrice`（实时 ETF 价） | 用基准日恒定 H_i，不依赖实时价 |

## 十一、常见 AI 易犯错误

1. **改实时估值前没读本文** → 不知道 hedge 魔法与 NAV 基准铁律，凭记忆手算。
2. **混淆 hedge 与 calibration** → hedge=LOF↔ETF，calibration=期货↔ETF，量级不同。
3. **把 501018 减法规则当符号错位** → USO 699 是整篮总数，纯美=699−EU−JP，规则对 N 区域通用。
4. **用 LOF 市价算篮子敞口** → 必须用 NAV（见第八节 bug）。
5. **忽视微型合约** → hf_GC= MGC(10oz)、hf_CL= MCL(100桶)，不是 GC/CL。
6. **手算代替程序验证** → 东哥明确要求：让程序自判类型 + 真算（写脚本调 `arbcore` 引擎），别凭 AI 记忆手算乘法。
7. **误判"程序有 gap 算不出"** → DB hedge 空时 `fund_service.py` 会合成 calc_hedge，160719 期货对冲面板能算，勿断言"返回 null"。
