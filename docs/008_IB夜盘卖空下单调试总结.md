## ⚠️ 任何 AI 修改 ib_reader.py 前必须阅读（2026-07-17 强制执行）

### 关于 OVERNIGHT 交易所的铁律

1. **美股夜盘（OVERNIGHT 时段）有完整的 Level 1 实时行情（Bid/Ask/Last）。** GLD、XOP、USO、QQQ、SPY 等核心套利标的在 Overnight Session 流动性良好，有真实的买一价/卖一价。**AI 不得自作聪明猜测"美股夜盘没有盘口数据"、"夜盘没有流动性 BID/ASK"或擅自引入降级逻辑。** 这是 AI 反复犯的严重错误——总是假设夜盘只有成交价没有盘口，擅自改成快照模式或 SMART 兜底，导致买一价/卖一价丢失。**OVERNIGHT 时段有完整的买一/卖一/成交量数据，与日盘一样完整。**
2. **任何时候，行情订阅和下单路由只使用 `exchange="OVERNIGHT"`。绝对不使用 SMART 路由。** 该程序只在美股夜盘时段运行，不参与日盘交易。任何 AI 不得将 `exchange` 改为 SMART 或做动态切换（夜盘 OVERNIGHT / 日盘 SMART）。
3. **`primaryExchange` 在夜盘必须留空。** OVERNIGHT 路由不需要 `primaryExchange`，加了会导致 Sec-def 断连时的 Error 201 废单。
4. 如果前端外盘盘口显示"等待数据"但 IB 按钮是绿色：
   - 先检查后端控制台是否有 `已发起 GLD 夜盘长连接订阅`
   - 如果有，等 10-30 秒让 IB 推送第一个 tick
   - 如果长时间无数据 → **重启 IB Gateway**，这是最有效的修复手段
   - ~~AI 不得先入为主修改 exchange 或加 SMART 降级兜底~~

### 关于 `reqMktData` 行情订阅

`reqMktData(req_id, contract, genericTickList="", snapshot=False, regulatorySnapshot=False, marketDataOptions=[])` 使用空 `genericTickList` 即可获取完整的 Level 1 数据（Bid=1, Ask=2, Last=4, BidSize=0, AskSize=3）。OVERNIGHT 交易所会正常推送买一价和卖一价，不需要额外参数。

**⚠️ 严禁将 `snapshot` 改为 `True`。** 快照模式（`snapshot=True`）只返回一次成交价（Last），不推送实时 bid/ask，前端会显示"无买一价"或 bid=0。2026-07-17 AI 修改导致没有买一价/卖一价的根因就是这一步——要么改了 `snapshot=True`，要么在回调中错误过滤了 bid/ask 的 tickType。恢复 git 版本 `59091c8`（使用长连接 `snapshot=False`）后行情恢复正常。

## 二、错误清单（按时间顺序）

### 错误 1：Error 10268 —— 不支持"EtradeOnly"委托单属性

**现象：**

```
[4;2;2;10268;不支持"EtradeOnly"委托单属性。]
```

**原因：** `ibapi` 的 `Order` 类包含 `eTradeOnly` 和 `firmQuoteOnly` 属性。在某些 TWS/Gateway 版本中，这两个属性默认非 `False`，导致拒单。

**修复：** 在 `place_us_order()` 中显式设置为 `False`：

```python
order.eTradeOnly = False
order.firmQuoteOnly = False
```

**位置：** `arbcore/fetchers/ib_reader.py`，`place_us_order()` 方法中设置完 `outsideRth` 之后。

---

### 错误 2：orderId = 0 导致订单被拒

**现象：** TWS 日志显示 `orderId=0`，EtradeOnly 拒单后出现 orderId=0 或异常订单 ID。

**原因：** `reconnect()` 和 `connect_to_ib()` 没有重置 `next_order_id = None`，导致重连后 `reqIds(-1)` 的 `nextValidId` 回调可能不触发，订单 ID 为 None 或 0。

**修复：**

- `reconnect()` 开头加 `self.next_order_id = None`
- `connect_to_ib()` 开头加 `self.next_order_id = None`

**位置：** `arbcore/fetchers/ib_reader.py`

---

### 错误 3：连接成功但行情不推送（"等待数据"）

**现象：** IB 按钮绿灯，但前端盘口显示"等待数据"。

**原因：** `start_polling()` 只在第一次 `get_price()` 调用时懒加载触发。如果前端请求没触发 get_price，轮询线程不会启动。

**修复：** 在 `reconnect()` 连接成功后显式调用 `self.start_polling()`：

```python
if self.connect_to_ib():
    self.start_polling()
```

**位置：** `arbcore/fetchers/ib_reader.py`，`reconnect()` 方法。

> ⚠️ **2026-08-03 补充**：上述"懒加载未触发"是 2026-07 的旧根因。2026-08-03 又出现一类**新的「等待数据」根因**——并非订阅没启动，而是兜底快照把 `bid=ask=last` 写入、被 `market_data_service` 的 `bid==ask→None` 过滤丢弃，再叠加成交价伪装、看门狗被架空、SMART 违规。**完整根因与修复见第十节**，请勿再把"等待数据"简单归因于 Gateway 重连或"OVERNIGHT 不推流"。

---

### 错误 4：日志刷屏 —— "⏳ IB正在获取XXX，请稍后..."

**现象：** 多条日志反复出现：

```
⏳ IB正在获取GLD，请稍后...
⏳ IB正在获取USO，请稍后...
```

**原因：** 每次前端轮询调用 `get_price()` 时，只要 `ib_reader.prices` 中还没有该 symbol，就会打一次日志。87 只基金 × 15 秒轮询 = 大量刷屏。

**修复：** 添加限频机制，每个 symbol 每 30 秒只打一次日志。

**位置：** `ArbDashboard/backend/services/market_data_service.py`，`get_price()` 方法。

---

### 错误 5：IB 按钮显示绿色但实际未连接（卡死无法点击）

**现象：**

- 前端侧边栏 IB 按钮为绿色（success），点击无反应
- IB Gateway 无新 Client ID 窗口，后端日志无 `[IBReader] 尝试连接` 消息
- 但 `get_active_source_names()` 返回了 `"IB (Ready)"`，因为 `ib_reader.connected` 为 `True`

**原因：**  
`ib_reader.connected` 标志位被错误置为 `True`（可能来自历史重启、异常状态残留），而前端 `reconnectWithGuard(hasIb, 'IB', reconnectIB)` 在 `hasIb=true` 时直接 return，导致用户无法通过按钮重新发起连接。

**修复：** 移除 IB 按钮的 `reconnectWithGuard`，始终允许点击。后端 `reconnect()` 内部使用 `EClient.isConnected()`（真实 socket 检测）而非 `self.connected` 标记，所以即使已连接也不会有副作用。

```vue

@click="reconnectIB()"
:style="{ cursor: 'pointer' }"
```

**位置：** `ArbDashboard/frontend/src/layouts/MainLayout.vue`，IB 按钮的 `n-tag` 组件。

**诊断方法：** 后端日志无 `[IBReader] 尝试连接` + IB Gateway 无新 Client ID + 前端按钮绿色不可点击 = 命中此 Bug。

## 四、TWS 日志阅读指南

TWS 日志位于 TWS/Gateway 的 `ibgateway/jts/logs/` 目录下（而非项目目录）。

关键消息格式：

| 方向   | 格式                                    | 含义                                                |
| ---- | ------------------------------------- | ------------------------------------------------- |
| `<-` | `[3;2;0;XOP;...]`                     | OUT: 下单指令。3=版本, 2=消息类型, 0=orderId                 |
| `->` | `[4;2;2;10268;...]`                   | IN: 错误响应。4=版本, 2=消息类型, 2=reqId/orderId, 10268=错误码 |
| `->` | `[1;6;reqId;tickType;price;size;...]` | IN: 实时行情推送。1=tickPrice, 2=tickSize                |
| `->` | `[17;reqId;...]`                      | IN: 历史数据响应                                        |
| `<-` | `[20;reqId;...]`                      | OUT: 历史数据请求                                       |

**常见错误码对照：**

| 错误码       | 含义               | 处理方式                          |
| --------- | ---------------- | ----------------------------- |
| 10268     | EtradeOnly 属性不支持 | 设置 `order.eTradeOnly = False` |
| 2157      | Sec-def 数据场断连    | 忽略，不影响行情和下单                   |
| 2104/2106 | 数据场连接正常          | 正常信息                          |
| 2107      | 历史数据场未激活         | 正常信息                          |
| 2109      | OutsideRth 被忽略   | 良性警告                          |
| 201       | 合约不可卖空           | IB 侧限制，换标的                    |
| 502/1100  | 连接断开             | 触发重连                          |

## 七、行情订阅架构概要

```
IB Gateway
  → reqMktData(req_id, Contract(exchange="OVERNIGHT"), genericTickList="", snapshot=False)
  → tickPrice(tickType=1, price) → prices[sym].bid = price     # 买一价
  → tickPrice(tickType=2, price) → prices[sym].ask = price     # 卖一价
  → tickPrice(tickType=4, price) → prices[sym].last = price    # 最近成交价
  → tickSize(tickType=0, size)   → prices[sym].bid_size = size # 买一量
  → tickSize(tickType=3, size)   → prices[sym].ask_size = size # 卖一量
      ↓
market_data_service.get_realtime_quote() [IB 分支]
  → 仅当 bid>0 且 bid≠ask（真实盘口）才 return source="IB" + bid_size/ask_size
  → 否则不返回（前端走其他源 / 显示等待），绝不返回 bid=ask 单一值
      ↓
前端（Analysis.vue / LazyMode）显示 "IB"，买一/卖一价 + ×买一量/×卖一量
```

> ⚠️ **两条永久禁令（2026-08-03 新增，AI 反复踩坑）**：
>
> 1. **禁止成交价伪装盘口**：`Last`(tickType=4) 只能写 `last`，绝不 `bid=ask=last`。
> 2. **禁止历史/快照兜底**：不得用 `reqHistoricalData` 拉历史快照写 `bid=ask=last=price`；无实时盘口就返回 None。

## 八、关闭连接的生命周期

### 8.1 Gateway 面板行为（无需担心）

每次重启后端，IB Gateway 的 API 连接面板都会多一行 client 记录。**这是 Gateway 的设计**——每条连接记录永久保留，断开后只标记为 "Disconnected"，不会自动删除。每次新连接（即使是同一个程序重启）追加一个新行，这是正常行为，**不影响功能**。

### 8.2 完整连接生命周期

```
程序启动 → reconnect() → start_polling()
                            ├─ polling 循环（每 5 秒）
                            │   ├─ 检查夜盘时段
                            │   ├─ 维持 reqMktData 长连接订阅（OVERNIGHT，snapshot=False）
                            │   └─ 看门狗（长连接零真实 tick >600s 则强制重连自愈，绝不写兜底价）
                            │
程序关闭 → lifespan yield → stop_polling()   ← 先停止轮询线程
                           → disconnect_from_ib()
                               ├─ EClient.disconnect() → 关闭 socket
                               ├─ time.sleep(1)        → 等 TCP FIN 发出
                               ├─ 清空 prices / last_tick_time（看门狗从零计时）
                               └─ logger.info("已断开")
```

## 九、陈旧数据强制重连看门狗（2026-08-02 新增）

### 9.1 解决什么问题

用户长期痛点：IB Gateway 处于"假连接"状态（TCP 已连、`connected=True`），但行情农场断开，  
既无实时 tick 也无历史快照兜底 → 前端盘口长期空白/旧价，只能手动重启 Gateway。  
既有看门狗（第八节 60s 兜底）只在"无 tick 时取安全快照"，若快照也取不到则束手无策。  
本看门狗让"连着却没数据"也能自愈，用户基本不必再手动重启 IB。

### 9.2 机制（严格复用既有安全方法，零新增违规）

- 独立守护线程 `_stale_watchdog_loop`（随 `start_polling()` 启动，随 `stop_polling()` 停止）。
- 触发四要件（AND）：① `connected` 且 `EClient.isConnected()` 真；② `is_us_night_session()` 真（此时本应有盘口）；  
  ③ `min(last_tick_time.values())` 停滞 > `stale_reconnect_threshold`（默认 600s）；④ 距上次强制重连 > `stale_reconnect_cooldown`（默认 600s，防抖动）。
- 动作：`stop_polling()` → `disconnect_from_ib()` → `reconnect()`。
- 红线遵守映射（详见第五节）：`disconnect_from_ib` 含 `sleep(1)`(7) 与 `prices`/`last_update_time` 清空(9)；  
  `reconnect` 含 `next_order_id=None` 重置(3) 与 `start_polling()`(4)；重订阅保持 `reqMktData(snapshot=False)`(10) 与全 tickType(11)。  
  本函数绝不动 `exchange`/`primaryExchange`/`order`(1/2/5)。
- 仅当长连接与历史快照兜底**双双失败**（前端长时间无盘口）才触发；正常行情下永不动。

### 9.3 关键防死锁设计

- 看门狗线程与轮询线程**分离**：`stop_polling()` 由看门狗线程调用，安全 join 轮询线程（非自 join）。
- `stop_polling()` 内对看门狗线程做"自 join 保护"：当前线程即看门狗线程时不 join，避免死锁。
- `start_polling()` 增加"已在运行则跳过"防重入，避免强制重连时新旧轮询线程叠加。

### 9.4 紧急恢复 / 回滚（出事前先读，出事不慌）

改动仅限 `arbcore/fetchers/ib_reader.py`（`__init__` 新增参数、`start_polling`/`stop_polling` 改动、新增 `_stale_watchdog_loop`），  
**不影响任何 exchange/order/snapshot 逻辑**。三种恢复方式任选：

1. **即时关闭（无需改代码、无需重启整站逻辑）**：在 `ArbDashboard/backend` 启动环境加  
   `ARB_IB_STALE_GUARD=0`，重启后端即可停用看门狗，其余逻辑不变。
2. **代码回滚**：`git revert f3dcbda` 或  
   `git checkout f3dcbda~1 -- arbcore/fetchers/ib_reader.py`，重启后端。
3. **临时放大阈值**：把 `__init__` 里 `stale_reconnect_threshold` 改 99999（≈永不触发），或 `stale_reconnect_cooldown` 改大。

### 9.5 验证要点

- 夜盘时段、IB 正常连接且有盘口：看门狗**不应**触发（日志无 "陈旧数据看门狗触发"）。
- 制造"假连接"（IB Gateway 连着但断开行情农场）超过 5 分钟：应出现一次  
  `[IB] 陈旧数据看门狗触发：...强制断开重连以自愈`，随后 `reconnect` 恢复长连接订阅。
- 非夜盘时段：即使 `last_tick_time` 旧，看门狗因 `is_us_night_session()` 为假而**不触发**。

## 十、2026-08-03「等待行情」Bug 完整根因与修复（多层叠加，AI 必读）

### 10.1 现象

- 周一 09:39 启动主程序后，IB 盘口（XOP/GLD/USO/SLV/INDA/QQQ/SPY）在「外盘/期货盘口」面板与实时沙盘均显示「等待数据」。
- IB Gateway 绿灯、TCP 已连、长连接订阅已发（日志有 `已发起 X 夜盘长连接订阅`）。
- 用户最初怀疑"昨天 AI 改的代码导致回归"。

### 10.2 第一层排查（排除误判，结论部分有误）

- 检查 git diff：昨日改动**只**是看门狗参数 + 防重入包装 + 新增 `_stale_watchdog_loop`，**未触碰** connect_to_ib / 订阅 / exchange / snapshot。
- 当时结论：不是代码回归，最可能是 Gateway 周末后需重登。
- ⚠️ **订正**：这一层结论不全面。真正的根因是**既有逻辑链**（兜底写假值 + 成交价伪装 + 看门狗被架空 + SMART 违规），与昨日改动无关；但昨日看门狗 `stale_reconnect_threshold=300` 与兜底冷却同频、且 `disconnect_from_ib` 没清 `_last_fallback_time`，确实放大了"长时间空白"。

### 10.3 根因链（从表象到本质，共 5 层）

1. **表象过滤**：`market_data_service.get_realtime_quote` 的 IB 分支有 `if bid == ask: return None`。
2. **兜底写假值**：`ib_reader._polling_loop_inner` 每 300s 调 `reqHistoricalData("BID")` 拉历史快照，写成 `prices[sym] = {bid=ask=last=price}`（单一值）。这个 `bid==ask` 的假盘口被步骤1过滤 → 返回 None → 前端"等待数据"。
3. **成交价伪装**（比兜底更本质）：`tickPrice` 收到 `Last`(tickType=4) 且 `bid==0` 时执行 `bid = ask = last = price`，把**成交价灌进盘口**。即使长连接推来真实 Last，盘口也被污染成 bid=ask。
4. **看门狗被架空**：看门狗用 `last_update_time` 判陈旧；该字段被 300s 兜底快照持续刷新 → 长连接零 tick 时看门狗永远不触发 → 无法自愈重连。
5. **SMART 违规**：`ib_reader.py:185` 抓前收盘的 `reqHistoricalData("1 D","1 day","TRADES")` 用了 `exchange=SMART`（仅 VIX 应走 CBOE）。夜盘用 SMART 触发 2157 等错误、无数据，违反铁律。

> 🔑 **核心真相**：OVERNIGHT 夜盘**本来免费推实时 tick（含 bid/ask/量）**，不是"不推 tick"。所谓"零 tick"是当时农场抖动/断连的暂时现象，被误读成"OVERNIGHT 不行要改 SMART"。用户经 IB 官方客服确认：**夜盘严禁 SMART，OVERNIGHT 正常推流**。此条已写入 AGENTS.md TOP1 铁律。

### 10.4 修复（对应每一层，[AI-2026-08-03]）

1. **彻底删除兜底快照循环**：`ib_reader._polling_loop_inner` 删掉整段 `reqHistoricalData` 写 `bid=ask=last=price` 的逻辑，替换为 `time.sleep(5)`。零兜底。
2. **tickPrice 去伪装**：`Last`(tickType=4) 只写 `last`，删除 `if bid==0: bid=ask=last`。
3. **market_data_service IB 分支**：仅 `bid>0 且 bid≠ask` 返回 IB（含 `bid_size`/`ask_size`）；否则不返回（前端走其他源/等待）。
4. **看门狗改用 `min(last_tick_time.values())`** 判陈旧（长连接真实 tick 时间）；`stale_reconnect_threshold` 300→600（>原兜底间隔，避免同频风暴）。
5. **disconnect_from_ib**：清空 `last_tick_time`（看门狗从零计时）；删除 `_last_fallback_time` 字段（`__init__` 注释、断连清空、hasattr 保护一并清除）。
6. **SMART → OVERNIGHT**（`ib_reader.py:185` 历史请求；VIX 仍 CBOE，不在禁列）。
7. **盘口数量**：`market_data_service` 返回补 `bid_size`/`ask_size`；前端 `Analysis.vue` + `LazyMode.vue` 显示 `×买一量/×卖一量`（详见第十一节）。

### 10.5 验证与教训

- 重启后端后 XOP 显示 `买一 172.68 × 14 / 卖一 172.90 × 1`——真·实时盘口 + 数量，正是目标。
- **给后续 AI 的告诫**：
  - 看到"等待数据"**不要**先归咎于"OVERNIGHT 不推 tick / 要改 SMART"——这是反复犯的严重错误。
  - **不要**为"怕空白"加历史快照兜底（写 `bid=ask=last`）——假数据比空白更糟，且会架空看门狗。
  - **不要**把成交价伪装成盘口（`bid=ask=last`）——用户要的是真实买一卖一，不是成交价。
  - 看门狗判陈旧必须用「长连接真实 tick 时间」(`last_tick_time`)，绝不能用被兜底刷新的 `last_update_time`。
  - 代码锚点 `exchange="OVERNIGHT"` 永不改；夜盘任何 `reqHistoricalData`/`reqMktData` 都用 OVERNIGHT（VIX 例外走 CBOE）。

### 10.6 「等待数据」排查清单（后续 AI 照此走）

1. IB 绿灯 + 后端日志有"已发起 X 夜盘长连接订阅"？→ 等 10-30s 让首个 tick 到。
2. 长连接是否真零 tick（日志无 `tickPrice`）？→ 可能是 Gateway 农场抖动/周末重登，重启 Gateway；看门狗会在零 tick>600s 自愈重连。
3. `realtime_quotes[sym]` 是否被 `bid==ask` 过滤？→ 查 `market_data_service` IB 分支，绝不能返回 `bid=ask` 单一值。
4. 是否有人加回兜底快照 / 伪装成交价？→ 立即删除（红线13/14）。
5. 历史请求是否用了 SMART？→ 改 OVERNIGHT（红线1）。
6. **⚠️ 启动解释器是否用错？（最易漏、2026-08-03 新增）** `等待数据` 不一定是 exchange/SMART/tick 问题——**用错 Python 解释器启动后端，IB 会直接全空**。机器上有系统 `Python311`、WorkBuddy 内置 `3.13`，只有 `ArbDashboard/.venv` 装齐 `ibapi+apscheduler+xtquant+akshare`。用错解释器典型症状：`No module named 'apscheduler'`、IB 盘口全空、富途/冻结调度器失效。后端必须用 `.venv` 启动；`main.py` 顶部已加护栏（非 `.venv` 直接 `sys.exit(2)` 拒绝），`start_dashboard.bat` 已锁定 `.venv` 且禁止回退系统 python。**AGENTS.md「启动与配置」已写明唯一启动方式，后续 AI 严禁用 `python main.py` 直接跑。**
   - 快速验证：看后端启动日志首行是否有 `[致命] 后端必须用项目虚拟环境启动`——有即说明用错了 python，立刻改用 `.venv/Scripts/python.exe main.py` 或双击 `start_dashboard.bat`。
